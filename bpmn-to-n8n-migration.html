What is a BPMN workflow engine?

A BPMN engine (e.g. Camunda, Flowable, Bonita) executes stateful, long-running processes defined by BPMN 2.0 XML — with explicit gateways, events, and persisted process state.

04 / Decisions

DMN decisions with n8n Data Tables

Decision Model and Notation (DMN) is the companion standard commonly used with BPMN to separate business rules from process flow. Many decision-table use cases can be implemented in n8n with Data Tables.

Workflow input
→
Query Data Table
→
Match rule
→
Route outcome
1

Store rules as data

Model input conditions, priorities and outcomes as rows that authorized maintainers can update independently of the workflow.

2

Evaluate in the workflow

Query candidate rows, apply comparisons in IF, Switch or Code nodes, and pass the selected result into the process.

!

Know the boundary

Data Tables do not natively execute DMN XML, FEEL, hit policies or decision requirement diagrams. Retain a DMN engine when those standards are required.

Migration pattern: translate straightforward DMN decision tables into versioned Data Table rules and regression-test their outcomes against the source DMN model.

07 / Challenges

Migration considerations, with clear patterns

1

Long-running execution

Wait nodes persist execution data. Our standard is a webhook callback, so no worker or in-memory process remains occupied while waiting.

2

Human interaction

WIL supplies the tenant-scoped inbox and supports approvals, event acknowledgement, messages and embedded CHEFS forms.

3

Compensation

Translate BPMN compensation into visible, testable rollback branches and reusable sub-workflows.

4

Standards portability

The target is an executable n8n workflow, not BPMN 2.0 XML. Preserve the source model and document traceability where required.

08 / State

Long-running processes are a supported pattern

At each human or external decision point, the workflow creates a WIL action and enters a Wait node configured for webhook callback. n8n persists the execution and provides a unique resume URL.

Create WIL action
→
Wait for webhook
··· days ···
WIL proxy callback
→
Resume with response

Durable

Execution context is stored by n8n rather than held in worker memory.

Secure callback

WIL keeps the resume URL server-side and proxies authorized user responses.

Operationally simple

No special concern merely because an execution waits for an extended period.

External business records remain appropriate when reporting, cross-process lookup, retention or domain ownership requires them. They are not required just to keep a Wait node alive.

On login, CSTAR tenant membership creates or resolves the matching n8n team project and reconciles managed access.

Explicit role synchronization

project:editor and project:viewer map predictably; editor wins. Other CSTAR roles remain available to WIL without accidental project grants.

Personal + team workspaces

Personal projects receive local pseudo-tenant mappings; CSTAR-backed team projects retain authoritative tenant IDs.

Actor-aware work queues

WIL targets a specific user, a CSTAR role or a CSTAR group within the selected tenant.

Multiple form submissions

Each WIL showform interaction can launch an authenticated CHEFS form and return its new submission ID to the waiting workflow.

Secure extensibility

Long-lived CHEFS keys and callback URLs stay server-side; the browser receives only scoped data and short-lived tokens.

11 / Playbook

Step-by-step migration playbook

1

Inventory BPMN models

List processes, start events, variables, gateways, timers, user tasks, integrations.

2

Classify migration patterns

Identify straight-through automation, callback waits, WIL user tasks, compensation and reusable sub-processes.

3

Convert triggers

Map each start event to a Webhook / Cron trigger; emit unique processId per instance.

4

Translate gateways

Use IF/Switch for XOR; branching + Merge node for AND; emulate inclusive with multiple IFs.

5

Configure WIL tasks

Choose approval, event or CHEFS form; target a user, CSTAR role or group; resume through the callback proxy.

6

Capture audit

Log each node transition to audit table; mirror BPMN history needs.

7

Translate waits & events

Use Wait for webhook callbacks and timers; preserve correlation and timeout behavior.

8

Test & shadow-run

Replay BPMN history against n8n outputs; diff outcomes before cutover.

Does n8n cover broader use cases than BPMN?

Yes. BPMN is a precise notation for process orchestration. n8n combines orchestration with a general-purpose integration and data automation platform, so the same hosted capability serves more delivery needs.

13 / Decision

Use explicit decision boundaries

✓

Human-task processes

Supported by WIL: inbox, actor targeting, approvals, events, messages, CHEFS forms and secure resume callbacks.

✓

Long-running processes

Supported by Wait: webhook callbacks preserve execution context without occupying a worker throughout the wait.

!

Strict BPMN interchange

Retain a BPMN engine when BPMN 2.0 XML portability or execution of externally supplied models is itself a requirement.

!

Validate exceptional semantics

Prototype event races, complex compensation or engine-specific behavior and prove operational controls before cutover.

14 / Recommendation
Recommendation

Proceed with confidence,
migrate with evidence

  • Most standard BPMN constructs have direct n8n nodes or established composition patterns.
  • Straightforward DMN decision tables can become maintainable n8n Data Table rules.
  • Webhook-based Wait nodes support durable long-running processes without occupying workers.
  • WIL and CHEFS provide the missing human-task layer as an implemented platform capability.
  • CSTAR automatically aligns tenants, n8n projects and managed user roles.
  • Migration also unlocks integration, data automation and responsible AI-assisted workflows.

Next step: select representative BPMN processes, build migration exemplars, and shadow-run outcomes before phased cutover.
