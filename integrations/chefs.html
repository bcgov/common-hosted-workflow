Integrating CHEFS with n8n

This guide is for workflow designers and client teams who want to use CHEFS (Common Hosted Form Service) forms in workflows hosted on the Common Hosted Workflow (CHW) platform (n8n plus the Workflow Interaction Layer, WIL).

CHW gives you three ways to connect a CHEFS form to a workflow. They solve different problems and can be combined in one workflow.

#PatternWho fills in the formWhere the form is shownWhat starts or resumes the workflow
ACHEFS Event SubscriptionAnyone with access to the CHEFS form (often the public)CHEFS itself (submit.digital.gov.bc.ca)CHEFS calls …/rest/custom/v1/chefs/<path> on submission, which fires an n8n Webhook (or resumes a CHEFS Resubmit Wait). CHEFS can also call the n8n Webhook URL directly, but then every submission and resubmission starts a new execution
BWIL Show Form actionA specific user, group or role chosen by the workflowThe Workflow User Portal, under the actor's actionsThe workflow is already running; a Workflow Interaction Layer node creates the action and waits
CPortal CHEFS Form triggerSigned-in portal users you allow (all, roles, groups, users)The Workflow User Portal, under TriggersThe user submits the form in the portal, which starts the workflow at a WIL Trigger node

Which pattern should I use?​

  • Pattern A suits public intake forms. CHEFS stays the system of record for the submission, and CHEFS features such as Recall, status history and email notifications keep working. It is the only pattern that supports resubmission (the submitter edits the same submission and the waiting workflow resumes).
  • Pattern B suits human steps inside a case: a reviewer completing an assessment form, a manager filling in a decision form. The workflow chooses who gets the form, can prefill it, and receives the result directly.
  • Pattern C suits internal staff starting a case from the portal (for example "Start a new trip plan") without giving them the n8n editor or a webhook URL.

Typical combinations:

  • A → B: a public applicant submits in CHEFS; a reviewer group then gets a Show Form action in the portal.
  • C → B: a staff member starts a request from the portal; a second staff member approves it with a form.

Before you start​

You need:

  1. A published CHEFS form, with you as an owner or form designer.
  2. A CHEFS API key for that form (CHEFS → Manage Form → API Key). Each CHEFS form has its own key.
  3. An n8n project the portal can see: either a team project linked to a CSTAR tenant, or your own personal project (see below). The portal only sees workflows and credentials in that project.
  4. For patterns B and C: the people who will use the form must be able to sign in to the Workflow User Portal and see that tenant.

Then read the page for your pattern, and keep Credentials, nodes and troubleshooting open as a reference.

Do I need a CSTAR tenant?​

No. A CSTAR tenant is only needed when other people take part in your workflow.

Every user who can sign in gets a personal project in n8n. The platform gives it its own tenant ID, so it appears in the Workflow User Portal's Tenant list like a team tenant. With only a personal project you can use all three patterns, but only for yourself:

PatternWith a personal project
A — Event SubscriptionWorks as usual: anyone who can fill in the CHEFS form can start your workflow.
B — WIL Show FormActions can only be assigned to you. You receive and complete the form under your personal project's Actions.
C — Portal CHEFS Form triggerAllowed Actors is fixed to your own email, so only you can run the trigger.

To involve other people (reviewer groups, roles, other users), use a team project linked to a CSTAR tenant. The personal project's tenant ID is generated by the platform; it is not a CSTAR tenant and gives no access to other people. See Personal project tenant mapping.
